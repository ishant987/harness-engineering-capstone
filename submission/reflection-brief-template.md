## Part 1 — Per-system

### System 1 — Agentic loop

1. **Loop control.** Quote the `stop_reason` sequence from one trace. Name the file and function that decides continue-vs-stop, and how.

→ In `/workspace/evidence/system1/claim_03_water_damage_trace.jsonl`, the six-turn sequence was `tool_use → tool_use → tool_use → tool_use → tool_use → end_turn`. Turn 3 called `request_clarification`, turn 4 recorded the new fact and called `classify_claim` plus `assess_severity`, turn 5 called `route_to_adjuster`, and turn 6 ended normally. The control decision is implemented in `claims_intake/loop.py` inside `run()`: `tool_use` executes the requested tools and continues, `end_turn` returns the final state, and any other stop reason raises `UnexpectedStopReason`. This means control flow follows the API's structured `stop_reason`, not text generated by the assistant.

2. **Anti-pattern.** Name one anti-pattern `test_antipatterns.py` checks for. What would break in your run if the loop used it?

→ The System 1 anti-pattern suite checks that the loop does not use string-membership tests against assistant text as a control-flow signal. My `/workspace/evidence/system1/tests.txt` test artifact covers this alongside the rest of the 30-test suite. If the loop searched generated prose for a phrase such as `"done"` or `"route"`, the `claim_03_water_damage` run could terminate incorrectly even though its structured sequence required five `tool_use` turns before `end_turn`. The test also protects against replacing `stop_reason` with an arbitrary integer iteration cap.

3. **Tool design.** Pick two tools with overlapping inputs. How do the descriptions prevent misrouting? What did a structured tool error let the agent do that a generic string would not?

→ `route_to_adjuster` and `escalate_to_human` are overlapping terminal choices: both finish intake and carry structured claim information, but their descriptions make the distinction explicit. Routing is for confidence of at least 0.6 after classification and severity are available, while escalation is for unresolved ambiguity, low confidence, missing critical facts, or a policy dispute. In my `claim_03_water_damage_trace.jsonl`, the model reached confidence `0.95`, assessed severity as `high`, and therefore used `route_to_adjuster` rather than escalation. Tool failures use fields such as `is_error`, `error_category`, `is_retryable`, and `message`, allowing the agent to distinguish a permanent validation problem from something retryable instead of treating every failure as an undifferentiated text string.

4. **Your numbers.** Quote the turn count and cost for one claim. How does it differ from the README sample, and why?

→ In `/workspace/evidence/system1/summary.md`, `claim_03_water_damage` required 6 turns and cost an estimated `$0.0260`. The complete first live run cost `$0.1402`, which is higher than the README's approximate `$0.05` Haiku example. Live model behavior varied from the course sample: several claims used longer tool sequences, and some current models ended early when they wanted additional information. I documented that difference in `/workspace/evidence/system1/live-model-note.txt` rather than modifying the supplied reference code or fixtures.

### System 2 — Context strategy

5. **The reduction.** From `budget.json`: baseline tokens, assembled tokens, reduction %. Which section dominates the assembled context, and why keep it verbatim?

→ `/workspace/evidence/system2/budget.json` and `run-output.txt` show a baseline of **38,708 tokens** and an assembled context of **16,912 tokens**, a **56.31% reduction**. The active-conversation section dominates at **15,789 tokens**, compared with 204 for case facts, 434 for the refund summary, and 503 for the subscription summary. The active segment is kept verbatim because it contains the unresolved, current payment-method issue where small details such as the exact failure code and new-card last four digits matter. Compressing that live working set would risk losing information needed for the immediate answer.

6. **Summarize vs preserve.** State the rule for what gets summarized vs kept byte-exact, citing your per-section token numbers.

→ The strategy summarizes conversation segments whose issues are already resolved and preserves the active unresolved portion verbatim. In my run, the resolved refund material became a **434-token** section and the resolved subscription material became **503 tokens**, while the active section remained **15,789 tokens**; the durable case-facts block used another **204 tokens**. These values are recorded in `/workspace/evidence/system2/budget.json` and `/workspace/evidence/system2/run-output.txt`. The design spends compression risk on historical information while retaining exact recent context where position and wording can still affect the current decision.

7. **Facts block.** Compare `eval.jsonl` to `eval_control.jsonl`. Which question regressed, and what does that prove?

→ `/workspace/evidence/system2/eval.jsonl` passed **6/6** evaluation questions with the full assembled context. In `/workspace/evidence/system2/eval_control.jsonl`, Q1 still passed but **Q6 failed** after the persistent case-facts block was removed. Q6 required the exact structured status token for the payment-method update, demonstrating that ordinary conversation compression alone did not reliably preserve that exact durable fact. The regression shows why a small explicit facts block is useful even when the rest of the context is well summarized.

### System 3 — Claude Code config

8. **Path-scoped rules.** Quote the glob frontmatter from one rule file. Why is it better than a directory-level CLAUDE.md for cross-cutting conventions?

→ `/workspace/evidence/system3/config/.claude/rules/api.md` declares `paths: - "src/api/**/*"` in its YAML frontmatter. The configuration validator in `/workspace/evidence/system3/validator.txt` returned `OK`, and the System 3 test artifact reports 35 passing tests. A path-scoped rule is preferable because it activates only for matching files and can express cross-cutting patterns without scattering additional `CLAUDE.md` files throughout the directory tree. The root `CLAUDE.md` explicitly states that `.claude/rules/` is preferred when conventions such as test-file rules need to apply across multiple locations.

9. **Forked skill.** Quote the `context: fork` and `allowed-tools` lines. What does running forked + read-only buy you? What breaks without it?

→ `/workspace/evidence/system3/config/.claude/skills/deploy-check/SKILL.md` contains `context: fork` and an `allowed-tools` list limited to `Read`, `Grep`, `Glob`, read-only git commands, and read-only `gh pr` inspection commands. My validator artifact reports `OK`, confirming that this configuration satisfies the project checks. Forking keeps verbose discovery output such as file enumeration, status information, and diff inspection out of the main conversation, returning only a compact verdict. The read-only allowlist limits blast radius: without it, a deployment-check skill could accidentally modify files, push changes, or perform deployment actions while supposedly only validating them.

10. **Scope.** From the validator output: project-level vs user-level scope. Give one example of each from this config.

→ `/workspace/evidence/system3/validator.txt` reports `OK`, while the validated `/workspace/evidence/system3/config/CLAUDE.md` describes the hierarchy explicitly. A project-level example is `./CLAUDE.md` together with `.claude/rules/` and `.claude/standards/`, which is committed to the repository and shared with the team. A user-level example is `~/.claude/CLAUDE.md` or a personal skill under `~/.claude/skills/`, which stays on one developer's machine and is not shared through version control. This separation prevents personal preferences from silently becoming team policy.

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?

→ I seeded **40 defects** into the warm SQLite tier, but the final run in `/workspace/evidence/system4/shift-output.txt` used `since=2026-04-27T00:00:00Z` and returned only **2 new defects**. `WarmStore.defects_since()` executes `SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?`, supported by the `idx_defects_ts` index defined in `shift_monitor/warm.py`. Filtering happens inside SQLite before prompt construction, rather than loading all 40 records and asking Claude to filter them. This pushes deterministic selection down into the storage layer and keeps the model's working set small.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?

→ `shift_monitor/recovery.py` defines `STALE_RESUME_THRESHOLD_MINUTES = 30`. An incomplete manifest whose last step is no more than 30 minutes old is resumed; a completed, empty, or older manifest starts fresh. The System 4 suite in `/workspace/evidence/system4/tests.txt` passed all **33 tests**, including recovery behavior. A fresh invocation is safer for stale work because the old model session may reflect an outdated shift working set, while injecting the already-captured findings as a compact summary preserves useful progress without carrying stale conversational state forward.

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?

→ `/workspace/evidence/system4/hot-state-size.txt` shows my `hot_state.json` was only **680 bytes**, far below the approximately 5 KB budget. The corresponding file is `/workspace/evidence/system4/hot_state.json`, and the scratchpad records that the successful run analyzed 2 new defects. A shift system runs repeatedly for an indefinite period, so allowing the always-loaded hot state to grow with every shift would eventually recreate the same context-window problem the architecture is intended to solve. Keeping hot state bounded makes future invocation cost and context size depend on the present operating state rather than the age of the deployment.

## Part 2 — Synthesis

14. **Three layers.** Point to a file/artifact for each layer and justify.

→ **Model:** `claims_intake/system_prompt.py` defines the model-facing insurance task, including claim types, severity rules, clarification behavior, and routing-vs-escalation guidance; the model's decisions are visible in `/workspace/evidence/system1/claim_03_water_damage_trace.jsonl`.

→ **Harness:** `claims_intake/loop.py` is the harness layer because it repeatedly invokes the model, executes requested tools, records tracing information, continues on `tool_use`, and exits on `end_turn`. The six-turn System 1 trace demonstrates this loop operating around the model.

→ **Orchestration:** System 4's `shift_monitor/pipeline.py`, `warm.py`, and `recovery.py` form the orchestration layer because they decide what data a fresh shift invocation receives, maintain state across invocations, filter warm storage, and decide resume vs fresh recovery. `/workspace/evidence/system4/shift-output.txt` demonstrates that layer selecting only 2 new defects from a warm store containing 40.

15. **Deterministic vs prompt.** Cite one behavior guaranteed in code and one guided by prompt. When is each right?

→ A deterministic example is the terminal-tool enforcement in System 1: `route_to_adjuster` refuses to run until classification and severity exist, and a second terminal action is rejected once `session.terminal_called` is true. The passing System 1 test artifact `/workspace/evidence/system1/tests.txt` verifies these contracts independently of any single live model response. By contrast, deciding whether a claim is `property_damage`, `liability`, `theft`, or `auto` is guided by `system_prompt.py`; in the `claim_03` trace the model used the new water-source fact to choose `property_damage`. Deterministic code is appropriate for invariants and safety boundaries, while prompts are appropriate where judgment depends on natural-language evidence and cannot be fully reduced to fixed branches.

16. **Context, two faces.** Compare context management in System 2 (intra-session) and System 4 (cross-session) with cited numbers from both. Same principle, different mechanism — how?

→ System 2 manages context inside one long conversation: `/workspace/evidence/system2/budget.json` reduced **38,708 raw tokens to 16,912**, a **56.31% reduction**, by summarizing resolved segments while preserving active context and a durable facts block. System 4 applies the same principle across separate sessions: the warm database held **40 defects**, SQL pre-filtering supplied only **2** to my final shift run, and `/workspace/evidence/system4/hot-state-size.txt` shows the persistent hot state stayed at **680 bytes**. Both architectures separate durable signal from historical bulk. System 2 achieves that with summarization and positional assembly inside a conversation, while System 4 achieves it through storage tiers, SQL retrieval, scratchpads, and fresh model sessions.

17. **Reliability you can't see in one run.** Name one behavior a test guarantees that a single successful run would not reveal. Why does it matter before shipping?

→ System 1's `test_antipatterns.py` statically checks that `loop.py` does not use magic-string searches in assistant prose or an integer-literal iteration cap as its primary stop mechanism. A single successful `claim_03` trace cannot prove those anti-patterns are absent because the problematic branch might simply not be exercised during that run. `/workspace/evidence/system1/tests.txt` therefore gives stronger assurance than manual observation alone. This matters before shipping because an apparently successful demo can hide brittle termination logic that fails on different model wording or longer conversations.

18. **Blast radius.** Pick one system. What's the blast radius if it misbehaves, and what's the kill switch? Ground it in that system's tools, enforcement points, and state.

→ In System 1, the blast radius of a bad decision is a claim being sent to the wrong adjuster queue or being handled automatically when it should have been reviewed. The first safety boundary is the tool contract: `route_to_adjuster` requires prior classification and severity, and only one terminal action is allowed. The operational escape hatch is `escalate_to_human`, which the prompt directs the model to use when confidence is below 0.6 or critical facts remain unresolved. `/workspace/evidence/system1/claim_03_water_damage_trace.jsonl` demonstrates the normal terminal path, while `/workspace/evidence/system1/live-model-note.txt` shows why retaining an explicit incomplete/escalation path matters when live model behavior does not satisfy the expected terminal contract.

## Part 3 — Honest assessment

19. **What broke.** One thing that failed first try in your environment, and how you fixed it.

→ System 1 initially failed before making a request because `anthropic==0.39.0` was installed with `httpx==0.28.1`, producing `TypeError: Client.__init__() got an unexpected keyword argument 'proxies'`. I fixed the environment, not the reference implementation, by installing `httpx==0.27.2`, after which the API runner executed normally. The subsequent test evidence is stored in `/workspace/evidence/system1/tests.txt`, and the live run output is in `/workspace/evidence/system1/run-output.txt`. I kept the source solution unchanged so the evidence still represents the supplied architecture.

20. **What you'd change.** One architectural decision you'd make differently, grounded in what you observed.

→ I would preserve the pure `stop_reason` loop but add a small recovery layer outside it for the case where the model returns `end_turn` without having called either terminal tool. My live System 1 evidence showed this exact condition: `claim_01_kitchen_fire` repeatedly ended after two turns because the model wanted a repair-cost estimate, and `/workspace/evidence/system1/live-model-note.txt` records that Haiku, Sonnet, and Opus all exhibited the issue. Rather than changing the inner loop or branching on assistant prose, the outer runner could classify this as a typed protocol violation and allow one bounded follow-up invocation reminding the model that it must route or escalate. That would retain the course's clean `stop_reason` contract while making production behavior more robust to current-model differences.
